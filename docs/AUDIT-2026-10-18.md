## Cheyenne's screenshot bug

### What she is actually running

Because of the failed deploys, the scan code in production is the old per-image design from April (`798b0e7`), not the batched one on main. In that design:

1. Each screenshot is compressed and uploaded to Supabase Storage.
2. One `parse-recipe-image` call is made per screenshot, in parallel.
3. Each call sends the image to **Sonnet 4.6** with a **9 second** SDK timeout, and on any error retries once with another 9 seconds.
4. The partial recipes are merged on the phone.

A single screenshot usually finishes inside 9 seconds. Three text-dense screenshots mean three parallel Sonnet calls on a slower, larger output, and each one tends to blow the 9 second timeout. When all of them fail the client throws `Image N: Recipe image parsing failed: Request timed out (HTTP 500)`, which is the "errors out" she sees. When only some fail she gets a half recipe with a warning.

That 9 second number was chosen in April when the Netlify timeout was believed to be 10 seconds. It is not. The site is on the Pro plan with no custom timeout, and Netlify's current limit for synchronous functions is **60 seconds** on every plan. The code was starving itself.

### What is on main (unshipped)

The rewrite already fixes the design: all tiles go to **Haiku 4.5** in **one** call with a 50 second budget, the model merges overlapping screenshots itself, and the server returns friendly 4xx/5xx copy. I measured it against the real API with three overlapping synthetic phone screenshots of an 18-ingredient, 8-step recipe:

| Input | Model time | Result |
|---|---|---|
| 1 screenshot | 7.8s | 18 ingredients, correct |
| 3 overlapping screenshots | 12.4s | 18 ingredients, 8 steps, no duplicates, correct |

Well inside 60 seconds, and the dedup across screenshots works. So the fix is mostly "ship what is on main", plus the hardening below.

### What I would still change in the scan path

1. **Status copy is wrong.** [ScanRecipeForm.jsx:11](../src/features/cookbook/ScanRecipeForm.jsx) estimates `4 + 2 × photos` seconds; three screenshots say "about 10 seconds" and really take 15 to 20 with upload and cold start. Say "about 20 seconds" and show a progress stage so she does not think it hung.
2. **Verify on the real site after deploy.** Nothing in the new path has run in production yet. I will run a three-screenshot scan from the deployed app and read the function log for duration. If Netlify ever reverts to a shorter limit, the symptom will be a gateway 502 with an HTML body, which the client already maps to a readable message.
3. **Same 9 second trap in the pantry/receipt scanner.** [claude-scan.js:154-162](../netlify/functions/claude-scan.js) has the identical 9s-then-9s-again pattern, and it retries on *any* error (a 400 for a bad photo gets billed twice and takes 18s). Use `makeClient()` and the deadline budget like the recipe functions, and fall back only when the beta parameter is rejected.
4. **Pantry/receipt photos are not resized before upload.** [PhotoScanner.jsx:7](../src/components/PhotoScanner.jsx) allows 10MB files and [useScanSession.js:95-105](../src/hooks/useScanSession.js) sends them as base64 JSON. Base64 adds a third, Netlify caps the body at 6MB, so any photo over about 4.5MB fails with a bare "Scan failed". The recipe path already has a canvas resize in `recipeScan.js`; reuse it here.
